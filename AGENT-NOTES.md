# Agent notes — what this checkout has beyond stock career-ops

Read this before answering anything about scanning, applying, or editing files
under `automation/`. A pointer to this file is installed into the career-ops
checkout's `modes/_custom.md`, which is how you were sent here.

This checkout has additions that upstream career-ops does not ship, installed
from a separate repo (`career-ops-dk`). Read this before answering questions
about scanning, applying, or editing anything under `automation/`.

## What is installed here beyond stock career-ops

- **`providers/jobindex.mjs`** — scans Jobindex.dk, Denmark's largest job board,
  via its public RSS feed. Auto-discovered by `scan.mjs`; nothing to configure.
  It is the highest-yield source in this setup: one scan returned 13 Danish
  product roles against 2 from all ten configured company boards, and it is the
  only source reaching the enterprise and public-sector tier.
- **`automation/run-chain.sh`** — the whole pipeline in one command:
  scan → liveness → bridge → triage → evaluate → merge → reconcile → verify.
  `--limit N`, `--parallel N`, `--dry-run`, `--no-scan`.
- **`automation/pipeline-to-batch.mjs`** — converts `data/pipeline.md` into
  `batch/batch-input.tsv`. Upstream ships nothing that does this.
- **`automation/apply-queue.mjs`** — exports application bundles (below).
- **`automation/sync-reapply-windows.mjs`** — regenerates `re_apply_windows` in
  `config/profile.yml` from tracker rows.

## Applying to a role — the actual workflow here

Do NOT hand-fill forms or improvise an application flow. It is two steps:

```bash
node automation/apply-queue.mjs --min-score 4.0      # export bundles
cd ../career-ops-dk/apply-runner
uv run python run.py <handoff-dir> --dry-run         # verify, free, no browser
uv run python run.py <handoff-dir>                   # fill the forms
```

`apply-queue.mjs` writes one self-contained directory per job to
`../handoff/NNN-slug/` — `job.json`, `cv.pdf`, `cv.md`, `facts.md`, and
`cover-letter.md` when one exists. A bundle needs a tracked row with status
`Evaluated`, a report, and a generated CV PDF; run the `pdf` mode first if the
CV is missing.

`--min-score` defaults to 4.0, which is this project's own advice-against
line. Lowering it is the user's decision to make explicitly each time — offer
it, do not apply it silently.

### Which CV gets attached

`config/profile.yml`:

```yaml
cv:
  attach: tailored              # default: the per-role CV from the pdf mode
  attach: "data/My_CV.pdf"      # or: always attach this one, unchanged
```

`--cv <path>` overrides it for one run. A configured path that does not exist
is a hard error — never fall back to the tailored CV, and never "helpfully"
substitute a file. `job.json` records `cv_mode` so a finished bundle says which
one travelled.

The tailored CV is still generated either way; this only decides what is
attached. If the user has set a fixed CV, do not argue them out of it, but do
say once that a hand-made PDF usually parses worse in an ATS than the generated
one, and that a fixed CV is not reordered toward each job's keywords.

**Nothing in this system submits an application.** The runner fills a form,
leaves it open in a browser tab, and stops; the user reviews and clicks Submit.
This is enforced in code (a shadowed click action), not just requested in a
prompt. Never look for a way around it, and never suggest one.

Cover letters are NOT generated by the chain. A bundle without one records
`cover_letter: null` and the runner leaves motivation fields empty. If the user
wants one, run the `cover` mode first — it is fact-gated — then re-export with
`--force`.

## Editing these files

`automation/*` and `providers/jobindex.mjs` are **installed copies**. Their
source of truth is the `career-ops-dk` repo, and `./setup.sh` overwrites them.

Editing them here works until the next install, then silently reverts. If the
user wants a change to one of them, make it in `career-ops-dk/overlay/...` and
re-run `./setup.sh` from that repo. `./setup.sh --check` reports drift;
`./setup.sh --pull` rescues an edit already made here.

This does not apply to anything else in the checkout — `portals.yml`,
`config/profile.yml`, `modes/_profile.md`, `cv.md` and everything in `data/`
and `reports/` are ordinary user-layer files, edited here as normal.

## Data stays on this machine

The `career-ops-dk` repo contains no personal data and nothing generated here
should be added to it. There is deliberately no offsite backup of the tracker,
reports or profile — if the user asks about backups, tell them to back up this
checkout the way they back up anything else they would not want to retype.
